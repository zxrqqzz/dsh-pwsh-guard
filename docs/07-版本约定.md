# 07 · 版本约定（SemVer 2.0.0）

> 依据：[Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/) 的三条核心规则，
> 加上 npm 对 `0.x` 的既有惯例，以及 DSH 自己的兼容判定语义（`docs/06` §2）。
> 本文是**发布纪律**，不是建议：改版本号前先对照本文 §3 的判定表。

---

## 1. 经典三条（semver.org 原文精神）

| 位 | 什么时候加 | 含义 |
|---|---|---|
| **MAJOR** `X.0.0` | 做了**不兼容**的变更 | 用户不改配置就会坏 |
| **MINOR** `x.Y.0` | 以**向后兼容**的方式新增功能 | 用户不改配置也能继续用，多出新能力 |
| **PATCH** `x.y.Z` | **向后兼容**的缺陷修复 | 行为更正确，用法不变 |

配套的四条硬规定：

1. 版本号一旦发布**不可覆盖**（npm 也不允许同版本重发），改错了只能发新版本。
2. `1.0.0` 之前属于「开发阶段」：npm 的 `^0.1.0` 只匹配 `0.1.x`，所以 **0.x 的 MINOR 位事实上就是 breaking 位**。
3. 优先用 `-rc.N` / `-beta.N` 预发布标识做试跑（DSH 的兼容判定让 prerelease 参与范围比较，见 §4）。
4. 版本号必须**只增不减**，不许回退到旧号。

---

## 2. 对本插件来说，「API」是什么

别人用这个插件的方式有三种，三者都算 API：

| 面 | 例子 | 谁受影响 |
|---|---|---|
| **配置面** | `cordis.patch.yml` 里的 `config:` 键 | 改配置的人 |
| **行为面** | 哪些命令会被拦、会收到什么提示 | **模型**（它看不见配置，只感受到行为） |
| **宿主面** | 依赖的 dsh 契约（hook 名、section API、sandboxPolicy） | 升级 dsh 的人 |

这是插件和普通库最大的不同：**行为面也算公开 API**。一条命令从「放行」变成「被 deny」，对模型就是破坏性变更，哪怕配置一个字没改。

## 3. 判定表（改代码前对照）

### MAJOR（不兼容）

- 删除 / 改名 / 改语义的配置键（如 `slowMs` → `slowThresholdMs`，或 `denyOncePerSession` 默认值反转）。
- **`mode` 默认值从 `learn` 改成 `guard`**：没改配置的用户会突然开始被拦。
- 包名、入口（`main`/`exports`）、`name` 导出变化。
- `engines.dsh` 收紧到不再支持旧版 dsh（如从 `>=0.2.0` 收到 `>=0.3.0`）。
- 反馈通道变化：不再往工具结果追加耗时行，或 notice 从 `form: 'notice'` 改成别的东西。

### MINOR（新增 / 放宽 / 命中集变化）

- 新增配置键（必须带默认值，且默认行为与旧版一致）。
- **规则表的变化**：
  - 新增 high 规则、或把 medium 升级为 high → 可能拦住以前能跑的命令；
  - 新增 `bumpWhen` 危险区（node_modules、盘符根等）→ 同上；
  - 删除规则、降级 severity、放宽 allowlist → 只是少拦，但行为变了，也要让用户知道。
- 新增一类 notice（例如「被拦后重试」的提示）。
- `engines.dsh` 放宽（支持了更多新版本）。
- 守则段（prompt section）文本的实质改动：加一条新建议、改掉一条实测数字 —— 模型行为会变。

### PATCH（只修错）

- 修一个**明显写错**的正则，且修完后 `samples.hit/miss` 全部仍然通过（命中集不变）。
- notice / deny 的措辞、错别字、中文表达。
- 计时边界、类型守卫、空值兜底。
- 文档、注释、测试。
- 规则表里 `measured` / `why` 这类**说明字段**的补全。

### 三个边界情形的裁定

| 情形 | 定级 | 理由 |
|---|---|---|
| 修正则导致**命中集扩大**（原来漏拦的现在拦了） | MINOR | 行为面变了，用户要能看见 |
| 修正则导致**命中集缩小** | PATCH | 只往「少拦」方向走，是修复 |
| 只改 notice 里的耗时数字（本机实测数据更新） | PATCH | 不影响是否拦截，只影响说服力 |

## 4. 和 dsh 版本的关系

DSH 的兼容判定（`dsh-app-boot` → `evaluatePluginCompatibility`）只有两条路：

1. 有 `engines.dsh` → **只看它**；
2. 没有 → 检查 `@deepseek-ai/dsh*` 前缀的 peer 范围，prerelease 参与比较。

本插件采用**放行型**策略（`docs/06` §2.1）：

- peer 只声明 `@deepseek-ai/cordis`（**不参与**上述检查，因为前缀不是 `dsh*`）；
- **不写 `engines.dsh`**，所以任何 dsh 版本都能加载；
- 用 `npm run check:host` 做升级体检，而不是用版本号把门焊死。

因此：**dsh 升版本身不要求我们发新版**。只有下面两种情况才发：

| 情况 | 定级 |
|---|---|
| `check:host` 通过，代码无需改动 | 不发版 |
| 某个契约漂移，我们加适配/兜底 | 按影响：加了兼容分支 = MINOR；必须放弃旧 dsh = MAJOR |
| 决定开始声明 `engines.dsh` | MINOR（首次声明），之后每次收紧 = MAJOR |

## 5. 发布清单（每次发版照着做）

1. 对照 §3 判定表确定升哪一位，改 `package.json` 的 `version`。
2. 在 `CHANGELOG.md` 顶部加一节，用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 的分类：
   `新增 / 变更 / 修复 / 移除 / 安全`。
3. 规则表有变化时，在 CHANGELOG 里**明确写出哪条规则动了**（id + 从什么变到什么）。
4. 跑全绿：`npm test`、`npm run check:host`。
5. 打 tag：`git tag v<version>`（与 `package.json` 一致）。
6. 发布：`npm publish`（scoped 包记得 `--access public`）。

## 6. 当前版本

**`0.2.0`** —— 范围：

- 静态守则段（`guard:pwsh-efficiency`，852 字符，预算 1200 由测试锁定）；
- 慢命令计时 + **两条路**反馈（工具结果追加耗时行 + notice 给替代写法）；
- 规则表（`rules/rules.json`，10 条规则 + 5 条 allowlist）；
- 拦截通道（`mode: guard`）已在真实会话实测：拦一次 → 同规则第二次放行 → 逃生口静默；
- M3 会话内自适应：`predictiveAfter` / `predictiveMinMs` / `liftDenyOnceAfter`。

插件**默认仍是 `mode: learn`**（只提示不拦）；拦截只在你显式于 profile patch 里写 `mode: guard` 时打开。
所以从 `0.1.0` 升到 `0.2.0` 对默认配置是**纯增加**，判为 MINOR 成立。

之所以还不是 `1.0.0`：拦截在真实任务里只验证了几天，规则表还会调整（新增/升危规则按 §3 属于行为面变更）。
按 §1 第 2 条，0.x 阶段用 MINOR 位承载这类变更。等规则表与配置键稳定、默认模式切换完成后，再发 `1.0.0`。

### 升级路径

| 版本 | 内容 |
|---|---|
| `0.1.x` | M1：守则段 + 计时 + 两条路反馈（`learn`） |
| `0.2.0` | M3 会话内自适应 + 计时口径修正；拦截通道实测通过（由 profile patch 打开） |
| `0.3.0` | 发布物料与 npm 分发（`files` 白名单、README/LICENSE、`npm pack` 验证） |
| `1.0.0` | `mode` 默认从 `learn` 改 `guard`（breaking）→ 正式承诺 SemVer |
