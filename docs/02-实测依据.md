## A. 模型看不到耗时（这是根因）

`dsh-tool-pwsh/lib/index.js` 里把一次运行整理成模型可见文本的函数（约 146–175 行）只拼：

```
stdout 正文（或 (no output)）
[timed out after Nms]      // 仅超时
[exit code: N]             // 仅非 0
```

**成功命令没有任何耗时字段。** 也就是说：一条跑了 3 分钟、正常返回的命令，到达模型时
和一条 3ms 的命令长得一模一样，只多了几行输出。模型没有「我刚烧了多久」这个信号，
自然不会有优化动机。这是「AI 不主动优化」的第一性原因，比提示词写得好不好重要得多。

同一文件 256 行的工具描述里也没有任何性能守则，只提到「每次调用是新 pwsh 进程」
（等于每次都没有缓存红利，慢命令的代价被放大）。

## B. 外部程序在沙箱 shell 里不可用（这条改变了整套规则表）

| 试法 | 结果 | 来源 |
|---|---|---|
| `& rg.exe --version`（DSH 自带路径） | `Access is denied`，可复现 | 实测 |
| `& git --version 2>&1` | 抛 `Access is denied`；再试一次返回**空字符串**（静默失败） | 实测 |
| `& cmd /c "echo hi"` / `& node --version` | `Access is denied` | 实测 |
| `Start-Process rg.exe -Wait -RedirectStandardOutput file` | **成功**，输出 `ripgrep 15.0.0 (rev 3a612f88b8)` | 实测 |
| `Start-Process git … -RedirectStandardOutput file` | 报 `Access is denied`，**但文件里真写入了** `git version 2.54.0.windows.1` | 实测 |
| `Get-Command rg / fd / jq` | 全部不存在 | 实测 |
| `Get-Command git` | 存在（`D:\Xjk\App\Git\cmd\git.exe`，2.54.0） | 实测 |

**结论（写进规则表的前提）：**

1. 工具描述里已经写明：confined 模式（read-only / workspace-write）下进程**不能开命名管道**，
   而 PowerShell 的 `&` 正是靠管道抓 stdout → 所以 `& exe` 必然失败或返回空。
   这不是机器坏了，是沙箱设计边界。
2. 所以任何 `rg`、`fd`、`git ls-files`、`node -e` 的「快命令」建议，在壳里**跑不起来**。
   规则表的 `fast` 字段必须只含**进程内能完成**的写法（cmdlet / .NET API / provider 参数），
   或者明确指向「改用 DSH 内置的 grep / glob 工具」。
3. 需要外部程序时唯一稳定形是 `Start-Process -Wait -RedirectStandardOutput <file>` 再读文件，
   但代价（启动进程 + 落盘 + 再读）对「快」这个目标没有吸引力，不作为推荐。

## C. 性能实测（同一棵树，冷启动，12,357 个 .js 文件）

树 = `C:\Users\31813\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh\node_modules`

| 写法 | 耗时 | 说明 |
|---|---|---|
| `Get-ChildItem $t -Recurse -File -Filter *.js` | **2,693 ms** | 已经带了 `-Filter`（provider 层过滤），仍要 2.7s |
| `[System.IO.Directory]::EnumerateFiles($t,'*.js','AllDirectories')` | **1,193 ms** | 同结果数（12,357），快 2.3x；不产生 PS 对象 |

补充说明：

- 一次 `rg --files -g *.js` 的对照组**测量失败**（spawn 被拒，见 B），所以**没有** rg 的耗时数字，
  不要引用。「rg 是 ms 级」属于推断：DSH 内置 grep 工具用的是打包的 ripgrep，
  在宿主进程里跑，绕过了沙箱 → 这才是本机「ms 级」的真实路径。
- 项目真实体量比这颗树大一个数量级时（+ `node_modules` 嵌套 + OneDrive/网络盘），
  2.7s 会变成几十秒到几分钟——与用户描述吻合。

## D. 内核 API 契约（实现时必须贴着这几个签名写）

### D1. 执行前拦截：只能 allow / deny / cancel / ask，**不能改参数**

`dsh-tools/lib/types/index.d.ts`：

```ts
export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string; info?: ToolErrorInfo }
  | { kind: 'cancel' }
  | { kind: 'ask'; reason?: string; displayReason?: {...} };

'tools/pre-execute'(exec, next): Promise<PreToolDecision>
```

→ 只能「拦 + 给理由」，模型看到 reason 后自己重写。**静默改写只能走执行器层（C 方案）。**

### D2. 事后反馈：可以附加上下文

```ts
export type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] };
```

→ `additionalContexts` 就是「把一条 notice 塞进下一次请求」，不污染工具结果的原文。

### D3. 常驻守则：注册一个 prompt section

`dsh-system-prompt/lib/types/index.d.ts`：

```ts
export interface PromptSection {
  readonly name: string;      // 唯一，重复注册会抛
  readonly order: number;     // 升序拼接
  readonly text: string | ((context: AssembleContext) => string);
}
section(section: PromptSection): () => void;
```

→ `text` 支持函数 → 可以在**每次装配时**读 store 生成「本项目最近踩过的慢命令」，
这就是「结合本项目、用于次上下文」的落点。

### D4. 现成范例（照抄它的骨架就行）

`@deepseek-ai/dsh-repeat-tool-reminder/lib/index.js`（约 30KB，纯 ESM，零运行时依赖）：

- `ctx.on('tools/post-execute', async (exec, _result, next) => {...})`：先 `await next()` 拿下游决策，
  再把 `additionalContexts` 用 `prependContext()` 拼进去；
- 用 `createUserMessage({ content:[{type:'text',text}], source:{kind:'repeat-tool-reminder',form:'notice'} })`
  —— **`source.kind` 是必需的**，否则 notice 在历史里会被渲染成人话提问；
- `ctx.on('agent/pre-step', ({agent, messages}, next) => {...})`：用来在用户发新消息时重置计数
  （我们的「每会话只拦一次」可以复用这个重置点，或者干脆用 `exec.agent` 做 WeakMap 键）。

## E. 与 rtk 插件的关系（澄清，防止走错路）

`dsh-pwsh-rtk-rewrite` 的 README 自述：

- 它把 `execute(spec)` 子类化，先 `rtk rewrite "<cmd>"`，命中就把命令换成 `rtk <cmd>`。
- `rtk rewrite "Get-ChildItem"` → **exit 1，不改写**；pwsh cmdlet 与内建全部透传。
- 改写产物是**在命令前加 `rtk`**（`git status` → `rtk git status`），等于多一个进程。

→ 它优化的是「输出的字符数」，不是「执行时间」；对最痛的 `Get-ChildItem -Recurse` 完全无效。
两者可以共存（互不冲突：它动执行器，我们动 tool 层），但**不要指望它解决本项目的问题**。

## F. 环境勘误：壳是 Windows PowerShell 5.1，不是 pwsh 7

实测 `$PSVersionTable.PSVersion` = `5.1.26100.9818`。工具描述写的是 `pwsh -Command`，
但这台机器上实际跑的是 Windows PowerShell 5.1：没有 `System.Text.Json`，
`Get-Content` 默认按 ANSI 解码 UTF-8 文件（读中文会出乱码，JSON 会被误判非法）。

对规则表与实现的影响：

- 推荐的快写法在 5.1 全部可用（`EnumerateFiles` / `-TotalCount` / `-ReadCount 0` / `-List` 都是 5.x 就有）。
- **不要**写 7.x 专属语法（三目 `? :`、`&&` / `||` 管道链、`Get-Content -AsByteStream`）。
- 5.1 冷启动比 7 更贵（几百 ms），「每次调用新进程、没有缓存红利」这条更成立。
- 校验 JSON 用 `[System.IO.File]::ReadAllText($p,[Text.Encoding]::UTF8) | ConvertFrom-Json`；
  直接用 `Get-Content -Raw` 会被 ANSI 解码毁掉中文并误判 JSON 非法（本项目踩过）。
