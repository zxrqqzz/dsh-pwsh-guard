# 06 · 生态调研：语言、依赖、版本兼容

> 回答两个关键问题：**社区里"牛"的插件用什么语言写**、**长期跟 DSH 版本怎么维护**。
> 全部基于本机装机实测（web profile 24 个直接依赖 + 官方 304 个包），采样 2026-11-27。

---

## 1. 语言分布（实测，不是感觉）

### 1.1 官方（`@deepseek-ai/*`，本机 304 个包）

| 指标 | 数量 |
|---|---|
| 带 `.d.ts` 声明 | **302 / 304** |
| 带 `.ts` 源码 | 7（且都是零散工具脚本） |

→ 官方 100% 是 **TypeScript 源码 → 编译成 `lib/index.js` + `lib/types/*.d.ts`**。
但注意：这是**单体 monorepo 的构建产物**，分包发布。我们不是官方，没有那套 monorepo。

### 1.3 结论：TS 比例高，但原因是"有界面"

- **有 client UI 的插件全是 TS**（blender / pet / market / im / comfyui / plugin）：要用 React、要 tsdown 打包、有多模块。
- **host-only 的小而专插件全是纯 JS 零构建**，而且其中有跟我们最像的一类：
  `dsh-codegraph` 整个插件**就是一个 JS 文件**；`dsh-notify` 4 个；`dsh-workspace-acl-allow` 2 个。
- 也就是说：**语言选择跟"插件体量/是否有前端"强相关，跟"质量"不相关。**
  单文件能写完的守护类插件，社区里没人上 TS。

## 2. 版本兼容机制（长期维护的真正关键）

### 2.1 判定逻辑（`dsh-app-boot/lib/index.js` → `evaluatePluginCompatibility`）

```
有 engines.dsh        → 只看它，peerDependencies 全部忽略
没有 engines.dsh      → 逐个检查 peerDependencies 里 @deepseek-ai/dsh 或 @deepseek-ai/dsh-* 的范围
不满足                → 装载直接抛错：profile 起不来
```

原文（`pluginCompatibilityWarning`）：
> Plugin X is incompatible with dsh Y: requirements {...}. Running it may cause crashes or data loss.
> ... grant the exact-version exemption ... with `dsh plugin allow-version`

**关键细节**：spawn 检查只认 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` 前缀。
→ 只写 `@deepseek-ai/cordis` 的 peer，**兼容检查完全不管**，任何 dsh 版本都放行。
这就是 `dsh-notify` 只声明 `peerDependencies: {"@deepseek-ai/cordis": "^4.0.1"}` 的原因。

### 2.2 逃生口（CLI 真实支持，`dsh/lib/plugin-*.js`）

```powershell
dsh plugin version-exemptions                                   # 看已豁免
dsh plugin allow-version dsh-pwsh-guard@1.2.0 --dsh-version 0.2.1-rc.2 --accept-risk
dsh plugin revoke-version dsh-pwsh-guard@1.2.0 --dsh-version 0.2.1-rc.2
```

豁免写进 profile 的 `compatibility.json`，**精确到包版本 + dsh 版本**，不跨版本继承。

### 2.3 社区维护范围的真实写法

| 插件 | 范围写法 | 含义 |
|---|---|---|
| @jiangzhenguo/dsh-codegraph | `>=0.0.1-rc.1 <0.1.0 \|\| >=0.1.0-rc.1 <0.3.0-0` | 每验证过一个大版本就 OR 一段 |
| ds-harness-remote | `>=0.2.0-rc.1 <0.3.0-0 \|\| >=0.2.1-0 <0.2.2-0 \|\| ...` | 逐补丁 OR，最保守 |
| dsh-pet | `^0.2.0-rc.1` | 常规 caret |
| dsh-notify | 只写 cordis | 完全不管 dsh 版本 |

模式是「**验证过才加一段范围**」，靠 `^` 自动吃新版本的做法在社区里很少见（因为 prerelease 语义太坑）。

## 3. 长期维护的三个真实风险（按杀伤力排序）

### 风险 1：`@deepseek-ai/dsh-*` peer 写太紧 → 插件主动拒绝装载

dsh 升一个补丁版，`^0.2.0-rc.1` 之类范围就可能不满足 → **整个 profile 起不来**，
用户看到的是「dsh 打不开」，而不是「某个插件不兼容」。

**本项目策略**：peer 只写 `@deepseek-ai/cordis`（稳定、且不参与兼容检查）；
**默认不写 `engines.dsh`**；只有确认破坏时才收紧，并同时写 CHANGELOG 说明。

### 风险 2：事件/服务名漂移（没有编译期保证）

我们用的 5 个契约：

| 契约 | 用在哪 |
|---|---|
| `tools/pre-execute`（allow/deny/cancel/ask） | 拦截 |
| `tools/execute`（只观测） | 计时 |
| `tools/post-execute`（accept/enrich + `additionalContexts`） | 反馈 |
| `systemPrompt.section` + `getSectionOrder` | 守则段 |
| `ctx.get('sandboxPolicy').resolve({session})` | 判沙箱档 |

没有一处会编译报错，只有运行时才炸。**本项目策略**：

1. 所有 ctx 交互集中到 `lib/compat.js`，一处收口；
2. 每个 hook 里做**特性检测**（`typeof fn === 'function'`），缺失就安静降级（失败安全本来就是硬要求）；
3. 新增 `scripts/check-host.mjs` + `npm run check:host`：
   读**本机已装**的 dsh 包的 `.d.ts` 和 `lib/index.js`，字符串断言上面 5 个契约还在，
   输出「dsh 0.2.1-rc.2 · 5/5 契约在」或「第 3 条没了，反馈通道失效」。升级 dsh 后第一件事就运行它。

这条比任何 peer 范围都实在：**能在升级前 10 秒发现问题**，而不是等用户报告。

### 风险 3：本地/仓库安装的构建脚本被 pnpm 拦

`dsh plugin` 的官方提示原文：
> git-hosted plugins build on install via their `prepare` script, which pnpm blocks until allowed —
> add the exact key under `allowBuilds` in `pnpm-workspace.yaml`, then re-run

TS + 构建链 = 每次安装都要处理 `allowBuilds`，否则装不上。
**零构建 = 永远不踩这条**（也是 `dsh-notify`、`dsh-codegraph` 这类插件选纯 JS 的现实原因）。

## 4. 对项目的结论

| 项 | 结论 | 依据 |
|---|---|---|
| 语言 | **纯 JS（ESM）+ JSDoc 类型** | host-only 同类插件（codegraph / notify / session-manager / workspace-acl-allow）全是零构建 JS；VSCode 自带 TS 语言服务，`checkJs` 零安装就有类型提示 |
| 类型来源 | 手写 `types/dsh.d.ts`（子集，头注来源版本） | profile 里没有 `@deepseek-ai/dsh-*`，装不上也不用装 |
| 版本策略 | peer 只写 cordis；不写 `engines.dsh`；`check:host` 脚本做升级体检 | §2.1 的兼容判定只认 `dsh*` 前缀 |
| 工程形态 | 单包直出 | 同类插件全部单包；monorepo 只有官方/大前端项目 |
| 反馈失败 | 特性检测 + 安静降级 + 一次 `console.warn` | 风险 2 |

如果将来要加 client UI（设置面板、可视化规则编辑器），再迁 TS + tsdown —— 那时才有 React 和打包的必要。
